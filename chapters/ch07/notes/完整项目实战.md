## 7.3 表结构变更:password_hash

### 7.3.1 为什么不能存明文

数据库泄露的方式有很多:备份文件外流、运维误操作、SQL 注入、云服务商事故。如果密码是明文,泄露一次等于所有用户在所有网站的密码一起泄露(因为很多人复用密码)。

存储密码的正确做法是**存哈希,不存明文**,而且哈希必须不可逆。

### 7.3.2 哈希与加密的区别

| | 哈希(Hash) | 加密(Encryption) |
| --- | --- | --- |
| 能否还原 | 不能 | 能(有密钥) |
| 用途 | 存密码、校验完整性 | 传输敏感数据 |
| 例子 | argon2、bcrypt、SHA-256 | AES、RSA |

密码必须用哈希。加密是可逆的,一旦密钥泄露,所有密码都能被还原。

> **通俗理解**:哈希像把肉绞成馅——你能验证"这是不是同一块肉"(用同样的方式再绞一次比对),但没法把馅还原成肉。加密像上锁的箱子,有钥匙就能打开。

### 7.3.3 argon2 的用法

本项目使用 `argon2-cffi`。它的特点是**自带随机盐**、**参数可调**(内存、迭代次数、并行度),并且参数和盐值都写在哈希串里,不需要额外存字段。

```python
from argon2 import PasswordHasher

_hasher = PasswordHasher()

def hash_password(raw: str) -> str:
    return _hasher.hash(raw)          # 注册时:明文 → 哈希

def verify_password(raw: str, hashed: str) -> bool:
    try:
        return _hasher.verify(hashed, raw)   # 登录时:拿明文去校验哈希
    except (VerifyMismatchError, VerificationError, InvalidHashError):
        return False
```

**注意**:校验密码不能用 `hash_password(raw) == hashed` 比较字符串。因为每次哈希都会生成新的随机盐,同一密码两次哈希结果不同。

### 7.3.4 示例与运行结果

示例文件:`chapters/ch07/code/01_password_hash.py`

```plain
--- ① 同一个密码,哈希两次 ---
    第一次: $argon2id$v=19$m=65536,t=3,p=4$MfkBzFoTGauKkdLJZj9KBw$5fyU7MehnD7...
    第二次: $argon2id$v=19$m=65536,t=3,p=4$QpwLCTsvfYAquJ4taPPCeA$T+KZJwYPteBo...
    两次相同吗: False
    → 不同。因为 argon2 每次都会生成新的随机盐

--- ② 哈希串的结构 ---
    完整格式: $argon2id$v=19$m=65536,t=3,p=4$<盐值>$<哈希>
    算法    : argon2id
    参数    : m=65536,t=3,p=4  (内存 64MB,迭代 3 次,并行 4 路)

--- ③ 校验:正确密码 vs 错误密码 ---
    正确密码 secret123 → True
    错误密码 secret124 → False

--- ⑤ 耗时:故意让暴力破解变慢 ---
    单次哈希约 32.8 ms
```

单次哈希 32.8 毫秒,正常登录只算一次感觉不到;但暴力破解每秒只能试几十次。

> **通俗理解**:哈希故意设计得"慢一点"。正常用户一天登录几次无所谓,但攻击者想试一百万次就得花几个小时——这就是成本。

## 7.4 用户注册

### 7.4.1 流程

```plain
   ① schema 校验        用户名长度、手机号格式、密码长度
        │
        ▼
   ② 查重               用户名/手机号是否已存在  → 冲突返回 409
        │
        ▼
   ③ 哈希               明文 → argon2 哈希
        │
        ▼
   ④ 入库               INSERT,返回用户信息(不含密码)
```

### 7.4.2 实现

```python
# services/auth_service.py
def register(db: Session, username: str, phone: str, password: str) -> User:
    exists = db.scalar(select(User).where(or_(User.username == username, User.phone == phone)))
    if exists is not None:
        raise ConflictError("用户名或手机号已被注册")

    user = User(username=username, phone=phone, password_hash=hash_password(password))
    db.add(user)
    try:
        db.commit()
    except IntegrityError as exc:        # 并发下仍可能撞唯一键
        db.rollback()
        raise ConflictError("用户名或手机号已被注册") from exc
    db.refresh(user)
    return user
```

**注意**:即使前面查过重,`commit()` 仍要捕获 `IntegrityError`。两个请求同时注册同一个名字时,查重都会通过,只有唯一索引能挡住。

### 7.4.3 示例与运行结果

示例文件:`chapters/ch07/code/02_register_login.py`

```plain
--- ① 注册 → 201 ---
    状态码: 201
    响应: {'id': 436, 'username': 'reg63638', 'phone': '13000063638'}
    响应里有 password 吗: False   ← 响应模型已裁剪

--- ② 用同一个用户名再注册 → 409 ---
    状态码: 409  响应: {'detail': '用户名或手机号已被注册'}
```

## 7.5 用户登录与 JWT

### 7.5.1 登录流程

```plain
   ① 按用户名查用户     查不到 → 401
        │
        ▼
   ② 校验密码           哈希不匹配 → 401
        │
        ▼
   ③ 签发令牌           把用户 id 和过期时间打包,签名
        │
        ▼
   ④ 返回给客户端       以后的请求带在 Authorization 头里
```

**注意**:用户不存在与密码错误返回**完全相同**的提示,避免攻击者用"用户名不存在"来批量探测注册用户。

### 7.5.2 JWT 的结构

JWT 由三段组成,用 `.` 分隔:

```plain
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiI0MzYiLCJleHAiOjE3... . 签名
└──────────── header ────────────┘   └────────── payload ──────────┘   └ signature ┘
        算法声明                        用户 id、过期时间                 防篡改签名
```

| 部分 | 内容 | 是否加密 |
| --- | --- | --- |
| header | 算法(HS256) | 否,Base64 可解 |
| payload | `sub`(用户 id)、`iat`、`exp` | 否,Base64 可解 |
| signature | 用密钥对前两段签名 | — |

**注意**:payload 是**可解码的**,任何人都能看到里面写了什么。所以不要把密码、手机号等敏感信息放进去,只放用户 id 这类不敏感的标识。

> **通俗理解**:JWT 像一张盖了章的门票——票面信息谁都能读,但印章伪造不了。服务端不记录"谁买了票",只验章。

### 7.5.3 签发与校验

```python
# core/security.py
def create_access_token(user_id: int) -> str:
    now = datetime.now(timezone.utc)
    payload = {"sub": str(user_id), "iat": now, "exp": now + timedelta(minutes=settings.jwt_expire_minutes)}
    return jwt.encode(payload, settings.jwt_secret, algorithm=settings.jwt_algorithm)

def decode_access_token(token: str) -> int:
    payload = jwt.decode(token, settings.jwt_secret, algorithms=[settings.jwt_algorithm])
    return int(payload["sub"])
```

签名密钥放在配置里:

```python
jwt_secret: str = "dev-secret-change-me-please-0123456789"
jwt_algorithm: str = "HS256"
jwt_expire_minutes: int = 60
```

**注意**:密钥长度应不小于 32 字节。太短的密钥容易被暴力破解,PyJWT 会给出 `InsecureKeyLengthWarning` 警告。生产环境必须换成随机长字符串,并放在环境变量里。

## 7.6 鉴权依赖

### 7.6.1 get_current_user

定义在 `app/deps.py`,作用是从请求头里取出令牌、解析出用户:

```python
bearer_scheme = HTTPBearer(auto_error=False)

def get_current_user(
    credentials: HTTPAuthorizationCredentials | None = Depends(bearer_scheme),
    db: Session = Depends(get_db),
) -> User:
    if credentials is None:
        raise UnauthorizedError("缺少访问令牌")
    try:
        user_id = decode_access_token(credentials.credentials)
    except PyJWTError:
        raise UnauthorizedError("令牌无效或已过期")

    user = db.get(User, user_id)
    if user is None or user.is_deleted:
        raise UnauthorizedError("用户不存在或已注销")
    return user
```

三种情况统一返回 401:没带令牌、令牌无效/过期、用户不存在。

> **通俗理解**:`Depends` 是 FastAPI 的"前置检查"。你在路由参数里写 `current_user: User = Depends(get_current_user)`,FastAPI 就会在进函数之前先把用户解析出来;解析失败直接返回错误,函数根本不会执行。

### 7.6.2 require_role

角色校验用一个"依赖工厂"实现:

```python
def require_role(*role_names: str):
    def checker(current_user: User = Depends(get_current_user)) -> User:
        owned = {role.name for role in current_user.roles}
        if not owned & set(role_names):
            raise ForbiddenError(f"需要角色之一:{', '.join(role_names)}")
        return current_user
    return checker
```

使用方式:

```python
@router.post(
    "/{user_id}/roles",
    dependencies=[Depends(require_role("admin"))],
)
def assign_user_role(...): ...
```

### 7.6.3 401 与 403 的区别

| 状态码 | 含义 | 场景 |
| --- | --- | --- |
| 401 Unauthorized | 我不知道你是谁 | 没带令牌、令牌无效、令牌过期 |
| 403 Forbidden | 我知道你是谁,但你不能干这个 | 已登录,但角色不够 |

> **通俗理解**:401 是"请先出示证件",403 是"证件有效,但这一层不对外人开放"。

## 7.7 角色与权限

### 7.7.1 数据模型回顾

第五章已经建好三张表:

| 表 | 作用 |
| --- | --- |
| `roles` | 角色定义(admin / editor / viewer) |
| `user_roles` | 用户与角色的关联,联合主键防重复 |

模型中的关系:

```python
class User(Base):
    roles: Mapped[list["Role"]] = relationship(secondary="user_roles", back_populates="users")
```

### 7.7.2 角色接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/users/{id}/roles` | 无需登录 | 查询用户角色 |
| POST | `/users/{id}/roles` | **仅 admin** | 分配角色 |

实现:

```python
def assign_role(db: Session, user_id: int, role_name: str) -> list[str]:
    user = get_user(db, user_id)
    role = db.scalar(select(Role).where(Role.name == role_name))
    if role is None:
        raise NotFoundError(f"角色 {role_name} 不存在")
    if role not in user.roles:
        user.roles.append(role)
        db.commit()
    return [r.name for r in user.roles]
```

> **通俗理解**:角色就是"岗位标签"。接口本身不判断"这个人能不能删用户",而是先看"他有没有 admin 这个标签"。以后要加新岗位,只需要加一条角色记录,不用改代码。

## 7.8 事务:转账

### 7.8.1 为什么必须放在一个事务里

转账要改两行:甲方扣钱、乙方加钱。如果只成功一半:

```plain
   甲 -200  ✓
   乙 +200  ✗   ← 程序在这里崩了
   ─────────────
   结果:200 元凭空消失
```

必须保证两条 UPDATE 要么都生效,要么都不生效。这就是事务。

### 7.8.2 实现

```python
def transfer(db: Session, from_id: int, to_id: int, amount: Decimal) -> tuple[User, User]:
    if amount <= 0:
        raise AppError("转账金额必须大于 0")
    if from_id == to_id:
        raise AppError("不能给自己转账")

    src = get_user(db, from_id)
    dst = get_user(db, to_id)
    if src.balance < amount:
        raise AppError(f"余额不足,当前余额 {src.balance}")

    try:
        src.balance = src.balance - amount
        dst.balance = dst.balance + amount
        db.commit()                  # 两条 UPDATE 在同一个事务里
    except Exception:
        db.rollback()                # 任何一步出错,两边都撤销
        raise
    return src, dst
```

**注意**:`commit()` 只调用一次。如果先改成 `db.commit()` 两次,第二次失败时第一次已经生效,就回不去了。

### 7.8.4 并发下的隐患

本实现用"读出来改属性"的写法,并发时存在丢更新风险(详见第五章 5.6)。生产环境应改为:

```python
# 方案一:加锁读
stmt = select(User).where(User.id == 1).with_for_update()

# 方案二:原子 SQL
db.execute(text("UPDATE users SET balance = balance - 300 WHERE id = 1 AND balance >= 300"))
```

> **通俗理解**:两个收银员同时看余额 300,都以为够扣 200,结果各扣一次,余额变成 -100。要么让一个人先锁住账本,要么让数据库自己算,不要"先读再写"。

## 7.9 自动化测试

### 7.9.1 为什么要写测试

| 场景 | 没有测试 | 有测试 |
| --- | --- | --- |
| 改了密码逻辑 | 手动点一遍所有接口 | `pytest` 跑 8 个用例,10 秒出结果 |
| 别人接手代码 | 不知道哪些行为是"对"的 | 用例就是行为说明书 |
| 重构 | 不敢改 | 改完跑一遍就知道有没有坏 |

### 7.9.2 目录与 fixture

```plain
tests/
├── conftest.py      # 公共 fixture
└── test_auth.py     # 认证相关用例
```

`conftest.py` 提供两个 fixture:

```python
@pytest.fixture
def client():

@pytest.fixture
def temp_user(client):
    """注册一个临时用户,测试结束后自动删除。"""
    ...
    yield {"id": user_id, "username": username, "password": password}
    with SessionLocal() as db:      # 无论测试通过与否都会执行
        ...
```

| fixture | 作用 |
| --- | --- |
| `client` | 提供 TestClient,不用启动服务器 |
| `temp_user` | 造一个临时用户,结束后清理,用例之间互不影响 |

> **通俗理解**:fixture 就是"每次测试前帮你准备好的环境"。`temp_user` 像餐厅的试吃盘——测试用它,测完收走,不影响正式菜品。

## 7.10 常见错误

| 错误信息 | 原因 | 解决方法 |
| --- | --- | --- |
| `InsecureKeyLengthWarning` | JWT 密钥短于 32 字节 | 换成足够长的随机字符串 |
| `401 令牌无效或已过期` 但刚登录 | 服务端密钥被换过 | 重新登录获取新令牌 |
| `403` 但确认已是管理员 | 令牌是改角色之前签发的 | 重新登录;角色校验读的是数据库,通常无需重签 |
| `verify_password` 一直返回 False | 用了 `==` 比较哈希串 | 必须用 `hasher.verify()` |
| 注册返回 500 | 未捕获 `IntegrityError` | 在 `commit()` 外层捕获并转 409 |
| 转账后两边余额都变了但总额不对 | 调用了两次 `commit()` | 只提交一次,异常时 `rollback()` |
| 测试之间互相污染 | 用例没有清理数据 | 用 fixture 负责创建与销毁 |

## 7.11 本章小结

1. 密码只存哈希,不存明文;argon2 自带随机盐,同一密码每次哈希结果不同,校验必须用 `verify()`。
2. 注册流程为:校验 → 查重 → 哈希 → 入库;即使查过重,`commit()` 仍要捕获唯一键冲突。
3. 登录失败时,"用户不存在"与"密码错误"应返回相同提示,避免账号枚举。
4. JWT 的 payload 是可解码的,只放用户 id 与过期时间;签名密钥不得短于 32 字节。
5. 401 表示未认证,403 表示无权限;鉴权通过 FastAPI 依赖实现,可组合成 `require_role()`。
6. 涉及多表的写操作必须放在一个事务里,只 `commit()` 一次,失败时 `rollback()`。
7. 自动化测试用 `TestClient` + fixture,能覆盖状态码、响应结构与权限分支;本项目 8 个用例覆盖了认证主流程。
