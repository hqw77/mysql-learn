## 8.3 高频面试题

### 8.3.1 SQL 与数据库基础

**Q1. 什么是索引?为什么用 B+ 树?**

> **答题要点**
> 1. 索引是加速查询的数据结构,本质是"排好序的目录";
> 2. B+ 树层级低(通常 3 层)所以磁盘 IO 少;非叶子节点只存键、不存数据,一页能放更多键;
> 3. 叶子节点用链表相连,天然支持范围查询和排序。
>
> **加分**:对比哈希索引——哈希只能等值查询,不能范围;对比 B 树——B+ 树所有数据在叶子,查询稳定。

**Q2. 什么情况索引会失效?**

> **答题要点**
> 1. 对索引列做运算或函数:`WHERE YEAR(created_at) = 2024`;
> 2. 隐式类型转换:字符串列用数字查;
> 3. `LIKE '%abc'` 前置通配;
> 4. 联合索引不满足最左前缀;
> 5. 优化器判断走全表更快(数据量小、区分度低)。
>
> **加分**:用 `EXPLAIN` 看 `type` 和 `key`,`type=ALL` 就是全表扫描。

**Q3. 事务的 ACID 是什么?隔离级别有哪些?**

> **答题要点**
> 1. 原子性(要么全成要么全败)、一致性(约束不被破坏)、隔离性(并发互不干扰)、持久性(提交后不丢);
> 2. 四种隔离级别:读未提交、读已提交、可重复读(MySQL 默认)、串行化;
> 3. 对应解决的问题:脏读、不可重复读、幻读。
>
> **加分**:MySQL 的 RR 通过 MVCC + 间隙锁在大多数场景下避免了幻读,但并非绝对。

**Q4. 连接池是什么?参数怎么定?**

> **答题要点**
> 1. 建连接要走 TCP 握手 + 认证 + 会话初始化,比执行 SQL 贵得多;
> 2. 池化 = 复用 + 限流:预建一批连接重复用,并设上限保护数据库;
> 3. 关键参数:`maxconnections`(上限)、`blocking`(满了排队还是报错)、`ping`(借出前探活)。
>
> **加分**:实测 200 次 / 20 线程,裸连接 11.4 ms/次,池化后 2.66 ms/次,约 4.3 倍;池子不是越大越好,上限小于并发会排队。

### 8.3.2 ORM 与 SQLAlchemy

**Q5. ORM 和原生 SQL 怎么选?**

> **答题要点**
> 1. 常规增删改查、简单关联用 ORM:类型安全、防注入、可维护;
> 2. 报表、多表聚合、窗口函数、百万级导入用原生 SQL:可控、可优化;
> 3. 两者可共存,`session.execute(text("..."))` 就能执行原生 SQL。
>
> **加分**:ORM 替代的是样板 SQL,不是复杂 SQL。

**Q6. Engine 和 Session 有什么区别?**

> **答题要点**
> 1. Engine 管连接池,全程序一个;Session 是工作单元,每次操作用一个;
> 2. Engine 线程安全可共享;Session 不是,必须一线程一个;
> 3. Session 只在执行 SQL 时才向 Engine 借连接,用完立即归还。
>
> **加分**:`Session.close()` 是归还连接,不是断开——和第二/二章的池化是同一套机制。

**Q7. 什么是脏检查?什么时候发 UPDATE?**

> **答题要点**
> 1. 改属性只把对象标记为脏,不发 SQL;
> 2. `commit()` / `flush()` 时逐字段对比加载时的快照;
> 3. 没变就跳过;变了就生成 UPDATE,且只带变化的列。
>
> **加分**:所以赋相同的值不会产生 UPDATE;因为只更新变化列,多人改同一行不同字段不会互相覆盖。

**Q8. 什么是 N+1 查询?怎么解决?**

> **答题要点**
> 1. 查 1 次主表,再为每行补 1 次关联查询,共 1+N 次;
> 2. 触发场景:循环里访问懒加载关系、循环里 `session.get()`;
> 3. 解决:`selectinload`(1+1 条,用 IN 批量查)、`joinedload`(1 条 JOIN,但可能膨胀)。
>
> **加分**:实测 3 个用户,懒加载 4 条 SQL,`selectinload` 2 条;用户数增加时前者线性增长,后者不变。

**Q9. 并发扣款怎么防止丢更新?**

> **答题要点**
> 1. 先复现:两个事务读同一行、各自算、后提交的覆盖前一个;
> 2. 悲观锁:`SELECT ... FOR UPDATE`,第二个事务阻塞;
> 3. 乐观锁:加 `version` 列,`UPDATE ... WHERE version = 旧值`,影响 0 行就重试;
> 4. 原子更新:`SET balance = balance - 300 WHERE balance >= 300`。
>
> **加分**:ORM 的"改属性"生成固定值 UPDATE,天然有丢更新风险,扣减类操作建议直接写原子 SQL。

### 8.3.3 接口与工程实践

**Q10. 400、401、403、404、409、422、500 分别什么时候用?**

> **答题要点**
> 1. 400 业务参数不合法(格式对但业务不允许);
> 2. 401 未认证(没带令牌 / 令牌无效);403 已认证但无权限;
> 3. 404 资源不存在;409 资源冲突(唯一键重复);
> 4. 422 格式校验失败(FastAPI 自动);500 未捕获的异常。
>
> **加分**:我们项目里 422 由 Pydantic 拦下,404/409/401/403 由 service 抛自定义异常、`main.py` 统一映射。

**Q11. FastAPI 里怎么管理数据库 Session?**

> **答题要点**
> 1. `get_db()` 是生成器依赖:创建 Session → `yield` → `finally: close()`;
> 2. 路由参数写 `db: Session = Depends(get_db)`,FastAPI 自动注入;
> 3. `yield` 保证请求抛异常时也会关闭,连接一定归还。
>
> **加分**:Session 不是整个请求都占着连接,只在执行 SQL 时借、用完还。

**Q12. 密码应该怎么存?JWT 怎么用?**

> **答题要点**
> 1. 存哈希不存明文,用 argon2 / bcrypt,自带随机盐,校验用 `verify()` 不能比字符串;
> 2. JWT 三段:header.payload.signature,payload 可解码,只放用户 id 和过期时间;
> 3. 服务端无状态,只验签名;密钥不得短于 32 字节。
>
> **加分**:JWT 的缺点是没法主动失效,改密码后旧令牌仍然有效,要靠"版本号/黑名单"解决。

### 8.4.2 真实踩过的坑

这些都不是编的,是搭建过程中实际撞上并解决的:

| 坑 | 现象 | 原因 | 解决 |
| --- | --- | --- | --- |
| 关系映射报错 | `NoForeignKeysError` | 数据库没有物理外键,ORM 推断不出连接条件 | 两端都写 `primaryjoin="foreign(...) == ..."` |
| 迁移把表删了 | autogenerate 生成一串 `DROP TABLE` | 库里有 10 张未建模的练习表 | `env.py` 加 `include_object` 过滤 |
| `alembic.ini` 读不了 | `UnicodeDecodeError: 'gbk'` | 文件里有中文,Alembic 用系统编码读 | 该文件必须纯 ASCII |
| 连错库 | `Table 'test_db.users' doesn't exist` | 池子默认连 `test_db`,而 `users` 在 `learn_mysql` | 统一用 `MYSQL_DATABASE` 指定 |
| 迁移报注释差异 | `alembic check` 报 `modify_comment` | 模型注释改成英文逗号,库里还是中文逗号 | `ALTER TABLE ... MODIFY ... COMMENT` 对齐 |
| JWT 警告 | `InsecureKeyLengthWarning` | 默认密钥只有 20 字节 | 换成 ≥ 32 字节 |

> **通俗理解**:上面每一行,都是一个"文档里不会写、只有自己撞过才知道"的细节。面试时讲这些,比背概念更有说服力——因为它证明你真的动过手。

### 8.4.3 如果重做一次

| 现在的问题 | 更好的做法 |
| --- | --- |
| 转账用"读出来改属性" | 改用 `with_for_update()` 或原子 SQL |
| 测试直连开发库 | 用独立测试库 + 每个用例后回滚事务 |
| 没有日志配置 | 加结构化日志,记录请求 id 和慢查询 |
| 没有限流 | 登录接口加频率限制,防暴力破解 |
| 接口缺权限 | 目前只有角色接口限 admin,用户接口应加登录要求 |

## 8.5 简历怎么写这个项目

### 8.5.1 项目描述(一段话)

> 基于 FastAPI + SQLAlchemy 2.0 + MySQL 8.0 实现用户管理系统后端,采用 router / service / model 三层架构;
> 支持 JWT 认证与基于角色的权限控制,区分 401 与 403;密码使用 argon2 哈希存储;
> 用 Alembic 管理表结构变更,用 pytest 覆盖认证主流程;通过连接池与索引优化,将并发查询耗时降低约 4 倍。

### 8.5.2 可以展开讲的技术点

| 面试官可能问 | 你可以答 |
| --- | --- |
| 为什么用 FastAPI | 异步、自动生成 OpenAPI 文档、Pydantic 校验一体化 |
| 怎么做权限 | 依赖注入 + 角色校验工厂,`require_role("admin")` |
| 连接池怎么配 | `pool_size` / `max_overflow` / `pool_pre_ping`,按并发峰值估算 |
| 遇到过什么难题 | 无物理外键时的关系映射、autogenerate 误删表 |
| 怎么保证数据一致 | 转账放在一个事务里,只 commit 一次,失败 rollback |

## 8.6 下一步学什么

按投入产出比排序:

| 方向 | 为什么 | 建议起点 |
| --- | --- | --- |
| **Docker** | 让别人一条命令跑起来,作品集必备 | 写 Dockerfile + docker-compose(MySQL + app) |
| **测试覆盖率** | 现在只有认证 8 个用例 | 补转账、CRUD、角色接口的用例 |
| **Redis 缓存** | 高频查询走缓存,是最常见的性能优化 | 给"用户详情"加缓存,注意失效策略 |
| **消息队列** | 解耦耗时操作(发邮件、生成报表) | 用 Celery 或 RQ 做异步任务 |
| **MySQL 深入** | 索引原理、执行计划、锁机制 | 读《高性能 MySQL》,配合 `EXPLAIN` 实践 |
| **部署** | 从"能跑"到"能上线" | Nginx + uvicorn + systemd,或云服务 |

> **通俗理解**:你现在会"造一个能用的系统",下一步是"让它能被别人用、能扛住压力、出问题能查"。这三件事分别对应部署、性能、可观测性。
