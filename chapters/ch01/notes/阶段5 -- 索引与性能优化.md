## 2. 核心理论与必背概念
### 2.1 为什么要用索引？
+ **无索引**：相当于字典没有目录，查一个字要把整本书从头翻到尾（全表扫描，`type=ALL`）。
+ **有索引**：相当于字典有了拼音目录，直接翻到对应页（走索引，`type=ref`）。
+ **底层结构**：MySQL 默认使用 **B+ 树**。数据存在叶子节点，非叶子节点只存索引键，树的高度很低（通常 3 层就能存几千万条数据），所以查询极快。

### 2.2 EXPLAIN 核心列解析
在你的 SQL 前面加上 `EXPLAIN`，重点关注以下 4 列：

1. `type`** (访问类型)**：从好到坏依次为：
    - `system` > `const` (主键/唯一索引查询) > `eq_ref` (连表主键关联) > `ref` (普通索引) > `range` (范围查询) > `index` (全索引扫描) > `ALL`** (全表扫描，必须优化)**。
2. `key`：实际使用到的索引。如果是 `NULL`，说明没走索引。
3. `rows`：预估需要扫描的行数。数字越小越好。
4. `Extra`：
    - `Using index`：**覆盖索引（极品状态）**。表示只查索引就拿到了所有数据，不需要回表查数据行。
    - `Using where`：在检索出数据后，还需要进行过滤。
    - `Using filesort`：使用了文件排序（可能需优化）。

### 2.3 复合索引与最左前缀原则
+ **复合索引**：例如 `CREATE INDEX idx_city_age ON big_users(city, age);`。
+ **最左前缀原则**：复合索引 `(city, age)` 相当于建了 `(city)` 和 `(city, age)` 两个索引，但**不包含 **`(age)`** 的单独索引**。
    - ✅ `WHERE city = '北京'` 走索引。
    - ✅ `WHERE city = '北京' AND age = 25` 走索引。
    - ❌ `WHERE age = 25`**不走索引**（失效）。

### 2.4 索引失效的 4 大坑
1. **在索引列上做函数运算**：`WHERE YEAR(created_at) = 2026`。
2. **前导模糊查询**：`WHERE email LIKE '%99999%'`。
3. **隐式类型转换**：字符串列不用引号（如 `WHERE phone = 13800000000`，如果 phone 是 VARCHAR，则不走索引）。
4. **OR 语句**：如果 `OR` 的两边有一边没有索引，整体都会失效。

```plain
-- 1. 初始无索引时查询 email
EXPLAIN SELECT * FROM big_users WHERE email = 'user_99999@test.com';
-- 结果：type=ALL, key=NULL, rows=99822 (全表扫描)

-- 2. 添加索引
CREATE INDEX idx_email ON big_users(email);

-- 3. 再次查询
EXPLAIN SELECT * FROM big_users WHERE email = 'user_99999@test.com';
-- 结果：type=ref, key=idx_email, rows=1 (完美命中索引)
```

### 3.3 Python 代码测试执行计划   （慢查询监控）
在 `chapters/ch01/code/phase5/` 新建 `test_explain.py`。

```plain
import os

import pymysql
from pymysql.cursors import DictCursor

conn = pymysql.connect(
    host="localhost", user="root", password=os.getenv("MYSQL_PASSWORD", ""),
    database="learn_mysql", charset="utf8mb4"
)

def check_explain():
    with conn.cursor(cursor=DictCursor) as cur:
        # 查看无索引时的执行计划
        print("=== 无索引时的 EXPLAIN ===")
        cur.execute("EXPLAIN SELECT * FROM big_users WHERE age = 25")
        for row in cur.fetchall():
            print(f"type: {row['type']}, key: {row['key']}, rows: {row['rows']}")

        # 添加索引
        cur.execute("CREATE INDEX idx_age ON big_users(age)")
        conn.commit()

        # 再次查看执行计划
        print("\n=== 加索引后的 EXPLAIN ===")
        cur.execute("EXPLAIN SELECT * FROM big_users WHERE age = 25")
        for row in cur.fetchall():
            print(f"type: {row['type']}, key: {row['key']}, rows: {row['rows']}")

try:
    check_explain()
finally:
    conn.close()
```

**运行结果**：你会看到 `type` 从 `ALL` 变成了 `ref`，`rows` 从 10 万降到了几百。

3. **覆盖索引题**：把上面的 SQL 改为 `SELECT id, city, email FROM big_users...`，如果只建了 `(city)` 索引，会用到“覆盖索引”吗？（提示：看看 `Extra` 列有没有 `Using index`）

### 作业 1：写出一个索引失效的查询语句，用 EXPLAIN 证明。
**参考答案**：

```plain
-- 使用前导模糊查询，导致索引失效
EXPLAIN SELECT * FROM big_users WHERE email LIKE '%99999%';
```

**解析**：执行结果中 `type` 会变成 `ALL`，`key` 为 `NULL`，`rows` 为 10 万左右。这是因为 B+ 树是按字符从左到右排序的，如果最左边是 `%`，索引就无能为力。

### 作业 2：现有 SQL `SELECT * FROM big_users WHERE city = '北京' AND email LIKE 'user_999%';`。你会怎么建索引？为什么？
**参考答案**：

```plain
CREATE INDEX idx_city_email ON big_users(city, email);
```

**解析**：

1. **最左前缀原则**：因为 `city` 用的是 `=`（精确匹配），所以必须把 `city` 放在复合索引的最左边。
2. **模糊匹配规则**：`email LIKE 'user_999%'` 是后缀匹配（不含前导 `%`），可以走索引。所以可以放在 `city` 后面。

### 作业 3：把上面的 SQL 改为 `SELECT id, city, email FROM big_users WHERE city = '北京' AND email LIKE 'user_999%';`。如果只建了 `(city)` 索引，会用到“覆盖索引”吗？
**参考答案**：**不会。**  
**解析**：要触发覆盖索引（`Extra: Using index`），**SELECT 后面查询的字段必须全部包含在建的索引树中**。如果只建了 `(city)` 索引，而 SELECT 还需要 `id` 和 `email`，InnoDB 就必须拿着主键 ID 回到主表里去查这两个字段，这就叫**回表**。  
**改进**：如果想用到覆盖索引，需要建联合索引 `(city, email)`。因为 InnoDB 的二级索引默认会带上主键 `id`，建了 `(city, email)` 相当于 `(city, email, id)` 都在树上，此时 `Extra` 就会显示 `Using index`。  
 

## 5. 踩坑复盘记录
1. **建了索引但查询没变快？**
    - **解决**：用 `EXPLAIN` 看看 `type` 是不是还是 `ALL`。检查是不是踩了第 2.4 节的“四大坑”。
2. **忘记提交事务**
    - **解决**：在 Python 里执行 `CREATE INDEX` 等 DDL 语句后，记得执行 `conn.commit()`。
