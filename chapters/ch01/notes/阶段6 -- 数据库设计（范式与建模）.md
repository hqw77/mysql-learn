## 2. 核心理论与必背概念
### 2.1 三大范式（设计表的底线）
+ **第一范式（1NF）原子性**：表中的每一列都不可再分。
    - ❌ 错误示范：`address` 列存了“北京市朝阳区望京街道”。（如果业务需要按区搜索，这就违反了 1NF）。
    - ✅ 正确示范：拆分成 `province`, `city`, `district`。
+ **第二范式（2NF）唯一性**：必须有主键，且非主键列必须完全依赖于主键（主要针对联合主键）。
    - ❌ 错误示范：联合主键 `(order_id, product_id)`，但表里存了 `product_name`（只依赖 `product_id`，不依赖 `order_id`）。
+ **第三范式（3NF）直接性**：非主键列不能依赖于其他非主键列（消除传递依赖）。
    - ❌ 错误示范：`订单表`里有 `user_id`，又有 `user_name`、`user_phone`。（`user_name` 依赖 `user_id`，产生了传递依赖）。应该只存 `user_id`，需要名字时去 `用户表` JOIN。

### 2.2 什么时候需要“反范式”？
范式是为了减少数据冗余，但**JOIN 太多会导致查询极慢**。  
在互联网开发中，常常**故意打破第三范式**来用空间换时间。

+ ✅ **正确反范式**：订单表里冗余存一份 `product_name` 和 `product_price`。因为商品名字可能会改，但订单里的名字必须保留“购买那一刻”的，且不用每次查订单都去 JOIN 商品表。
+ ✅ **冗余统计字段**：在用户表里加一个 `order_count` 字段，每次下单 +1。这样查用户主页时不用每次都去订单表 `COUNT(*)`。

### 2.3 企业级建表规范（必背）
1. **表名与字段名**：全部小写，用下划线分隔（如 `order_items`），禁止用拼音，禁止用 MySQL 保留字（如 `desc`, `order`, `group`）。
2. **主键选型**：
    - `AUTO_INCREMENT` (自增ID)：最常用，性能好，但容易被爬虫猜到业务量。
    - `UUID`：全局唯一，但无序（会导致 B+ 树频繁分裂，性能差），通常不用作物理主键。
    - **雪花算法 (Snowflake)**：分布式系统首选，生成有序的 19 位 `BIGINT` ID。
3. **时间字段**：
    - `created_at`：记录创建时间（`DATETIME DEFAULT CURRENT_TIMESTAMP`）。
    - `updated_at`：记录更新时间（`DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`）。
4. **软删除**：不要轻易 `DELETE` 物理删除数据。加一个 `is_deleted TINYINT DEFAULT 0` 字段，删除时改为 1。
5. **状态字段**：尽量用 `TINYINT` 配合注释（如 0待支付，1已支付），不要直接存中文。

## 3. SQL 与 Python 实操案例：博客系统设计
**需求分析**：  
一个简易博客系统，包含：用户、文章、分类、标签（多对多）、评论。

**ER 图分析**：

+ 用户 1 : N 文章
+ 分类 1 : N 文章
+ 文章 M : N 标签（需要中间表 `article_tags`）
+ 文章 1 : N 评论（评论需要支持自关联，即“回复评论”）

### 3.1 建表 SQL (`sql/06-blog-design.sql`)
```plain
USE learn_mysql;

-- 1. 用户表
CREATE TABLE blog_users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL UNIQUE,
    password_hash VARCHAR(60) NOT NULL COMMENT '密码密文',
    is_deleted TINYINT(1) DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='博客用户表';

-- 2. 分类表
CREATE TABLE categories (
    id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(30) NOT NULL UNIQUE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='文章分类表';

-- 3. 标签表
CREATE TABLE tags (
    id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(30) NOT NULL UNIQUE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='标签表';

-- 4. 文章表
CREATE TABLE articles (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT UNSIGNED NOT NULL,
    category_id INT UNSIGNED NOT NULL,
    title VARCHAR(100) NOT NULL,
    content TEXT NOT NULL,
    view_count INT UNSIGNED DEFAULT 0 COMMENT '阅读量(反范式)',
    is_deleted TINYINT(1) DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='文章表';

-- 5. 文章-标签中间表（多对多）
CREATE TABLE article_tags (
    article_id BIGINT UNSIGNED NOT NULL,
    tag_id INT UNSIGNED NOT NULL,
    PRIMARY KEY (article_id, tag_id) -- 联合主键，防止重复关联
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='文章标签关联表';

-- 6. 评论表（自关联设计，支持回复功能）
CREATE TABLE comments (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    article_id BIGINT UNSIGNED NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL,
    parent_id BIGINT UNSIGNED DEFAULT NULL COMMENT '父评论ID，NULL表示一级评论',
    content VARCHAR(500) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='评论表';
```

### 3.2 如何用 Python 导出表结构？
在 `chapters/ch01/code/phase6/` 新建 `design_check.py`，用代码一键复盘你设计的表：

```plain
import pymysql

conn = pymysql.connect(
    host="localhost", user="root", password="你的英文密码",
    database="learn_mysql", charset="utf8mb4"
)

def show_tables():
    with conn.cursor() as cur:
        cur.execute("SHOW TABLES;")
        tables = cur.fetchall()
        print("=== 当前数据库中的表 ===")
        for t in tables:
            print(f"- {t[0]}")

try:
    show_tables()
finally:
    conn.close()
```

## 4. 阶段 6 验收作业与答案
**任务**：设计一个“简化的抖音/短视频系统”。  
包含需求：

1. 用户（`users`）：包含 `id`、昵称、手机号。
2. 视频（`videos`）：包含 `id`、作者ID、视频地址、文案、点赞数、发布时间。
3. 关注（`follows`）：用户之间多对多，A 关注 B。
4. 点赞（`likes`）：用户与视频多对多，记录谁在什么时候点赞了哪个视频，且**不能重复点赞**。

**参考答案 SQL**：

```plain
-- 1. 用户表
CREATE TABLE users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    nickname VARCHAR(50) NOT NULL,
    phone CHAR(11) NOT NULL UNIQUE,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='短视频用户表';

-- 2. 视频表
CREATE TABLE videos (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT UNSIGNED NOT NULL COMMENT '作者ID',
    video_url VARCHAR(255) NOT NULL,
    description VARCHAR(500),
    like_count INT UNSIGNED DEFAULT 0 COMMENT '点赞数(反范式：提高查询性能)',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='视频表';

-- 3. 关注表（多对多）
CREATE TABLE follows (
    follower_id BIGINT UNSIGNED NOT NULL COMMENT '关注者(粉丝)',
    followed_id BIGINT UNSIGNED NOT NULL COMMENT '被关注者(博主)',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (follower_id, followed_id) -- 联合主键，防止重复关注
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户关注表';

-- 4. 点赞表（多对多）
CREATE TABLE likes (
    user_id BIGINT UNSIGNED NOT NULL,
    video_id BIGINT UNSIGNED NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_id, video_id) -- 联合主键，防止同一人重复点赞
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='视频点赞表';
```

**答案解析**：

1. `follows`** 和 **`likes`** 表**：都是典型的多对多关系，且都要使用**联合主键**（`PRIMARY KEY (A, B)`）来保证唯一性。比如点赞表，用 `(user_id, video_id)` 联合主键，天然防止了重复点赞。
2. `videos`** 表的反范式**：在视频表中加了 `like_count` 字段，这样每次查视频流直接读字段就行，不用每次都 `COUNT(likes)` 表。

## 5. 踩坑复盘记录
1. **主键类型不统一**：设计时用户表用 `INT`，关联表却用了 `BIGINT`，会导致 JOIN 时隐式类型转换，无法走索引。**规范：主键和外键的数据类型必须严格一致。**
2. **忘加联合主键**：点赞表没写 `PRIMARY KEY (user_id, video_id)`，导致同一个用户疯狂点赞同一视频，插入了几千条重复数据。
3. **忘记反范式**：文章表每次都 `LEFT JOIN` 查分类，导致页面加载慢。**解决：像分类名字这种很少修改的数据，可以直接在文章表冗余一个 **`category_name`**。**
