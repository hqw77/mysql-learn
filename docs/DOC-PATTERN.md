# 教程文档排版模式

> 适用于 `chapters/chNN/notes/` 下的每一章。规则已按第 3 章的实战反馈调整为「知识 → 案例 → 排错 → 总结」。

## 0. 出发点

「边学边理解」的人有三个真实卡点：

| 卡点 | 表现 | 应对 |
| --- | --- | --- |
| 信息过载 | 读到一半走神，回来找不到位置 | 知识讲解和代码**分开放**，各看各的 |
| 没有成就感 | 讲了一屏原理，还没跑出一行结果 | 知识讲完立刻给**能跑的案例** |
| 看完不会用 | 懂了概念，遇到报错还是懵 | 每个案例带「怎么跑」和「能学到什么」 |

**核心设计**：正文只讲知识，代码全部拆成独立文件。读者可以只看知识，也可以边看边跑。

---

## 1. 四块结构

```plain
┌──────────────────────────────────────────────┐
│ 一、这一章讲什么                              │
│   1.1 全局地图（一张小图 + 角色表）            │
│   1.2 ~ 1.N 逐个知识点                        │
│      · 一句话定义                            │
│      · 为什么需要                            │
│      · 关键注意点（💡 / ⚠️）                  │
│      · 少量核心代码（≤15 行，完整版在案例里）   │
├──────────────────────────────────────────────┤
│ 二、可执行案例（分开给）                       │
│   开头一张总览表：案例 / 文件 / 验证什么 / 用时 │
│   每个案例固定 5 段：                         │
│     ① 验证什么   ② 怎么跑                    │
│     ③ 核心代码   ④ 你会看到（真实输出）        │
│     ⑤ 能学到什么                             │
├──────────────────────────────────────────────┤
│ 三、跑不起来怎么办（报错排查表）                │
├──────────────────────────────────────────────┤
│ 四、本章总结（三句话 + 验收清单 + 下一步）       │
└──────────────────────────────────────────────┘
```

## 3. 写作规则

| # | 规则 | 理由 |
| --- | --- | --- |
| 1 | 单章 300~400 行 | 第 3 章初版 529 行被反馈"密度过大" |
| 2 | 正文不贴完整代码，只贴核心 ≤15 行 | 全量代码在 `chapters/chNN/code/` 里 |
| 3 | 每个案例必须独立可跑 | 读者可以只跑其中一个 |
| 4 | 案例里的输出必须真跑出来 | 编的示例会误导 |
| 5 | `💡` 每个知识点最多 1 个，`⚠️` 只标真会报错的 | 标记一多就贬值 |
| 6 | 案例按「先简单后复杂」排序 | 案例 1 跑通再往下 |
| 7 | 每个案例最后必须有「能学到什么」 | 否则跑完不知道收获 |
| 8 | 术语首次出现配中文解释 | 别默认读者知道 |

## 4. 反例（前几版踩过的）

| 反例 | 问题 | 改法 |
| --- | --- | --- |
| 开头直接甩 `app/` 五层目录 | 还没跑通就先看架构 | 先给能跑的最小案例 |
| 11 个 Alembic 小节塞进同章 | 主线被支线淹没 | 拆成番外 |
| 正文里贴 60 行完整代码 | 长到没法边读边试 | 正文只留核心，全量进文件 |
| 只讲 `db.delete()` 不讲业务取舍 | 懂了 API 不会做决策 | 补业务场景问答 |

---

## 5. 交付方式

| 场景 | 给什么 |
| --- | --- |
| 开新章 | 先给「知识大纲 + 案例清单」，确认后再写正文 |
| 改文档 | 只给改动段落 + 前后对比 |
| 新增案例 | 落一个 `chapters/chNN/code/xx_yyy.py`，文档里链过去 |
| 长内容 | 正文只留主线，细节进 `chapters/extras/notes/` |
