# 教程文档排版模式

> 适用于 `notes/chNN/` 下的每一章。写新章、改旧章都按这个来。

## 0. 出发点

「边学边理解」的人有三个真实卡点：

| 卡点 | 表现 | 文档该怎么应对 |
| --- | --- | --- |
| 信息过载 | 读到一半走神，回来找不到位置 | 支持**跳读**：每节自带结论 |
| 没有成就感 | 讲了一屏原理，还没跑出一行结果 | **先给能跑的东西**，再拆原理 |
| 看完不会用 | 懂了概念，遇到报错还是懵 | 报错表 + 业务场景问答 |

结论：文档不是"讲完"，是**让人能多次进入**。

---

## 1. 三遍读法 → 三个区块

一份文档要同时服务三种阅读方式，所以结构上分成三个区块：

```plain
┌─────────────────────────────────────────────┐
│ 第 1 遍（5 分钟）：速览区                     │
│   · 顶部一句话总结                            │
│   · 第 0 节「五分钟速览」表格                  │
│   · Step 1 的代码 + 运行输出                   │
│   → 读完知道：这东西能干嘛、我能不能跑通        │
├─────────────────────────────────────────────┤
│ 第 2 遍（20 分钟）：讲解区                    │
│   · 拆解每一节（一个概念一节）                 │
│   · Step 2 / Step 3（进阶与工程化）           │
│   · 业务场景对话                              │
│   → 读完知道：为什么这样写、公司里怎么用        │
├─────────────────────────────────────────────┤
│ 第 3 遍（10 分钟）：自查区                    │
│   · 报错排查表                                │
│   · FAQ 满分模板                              │
│   · 验收清单                                  │
│   → 读完知道：我是不是真的会了                  │
└─────────────────────────────────────────────┘
```

## 3. 写作规则

| # | 规则 | 理由 |
| --- | --- | --- |
| 1 | 单章 300~450 行，超了拆番外 | 超过一屏滚动 8 次就会丢上下文 |
| 2 | 代码块 ≤ 40 行，必须能直接跑 | 太长就只能"看"，不能"试" |
| 3 | 每个代码块标明文件路径 | 读完知道该存哪 |
| 4 | `💡` 每节最多 1 个，`⚠️` 只标真会报错的 | 标记一多就贬值 |
| 5 | 三个以上并列项才用表格 | 两个用一句话就行 |
| 6 | 术语首次出现必须配中文解释 | 别默认读者知道 |
| 7 | 输出的数字、报错信息必须真跑出来 | 编的示例会误导人 |
| 8 | 每节结尾有一个「核心知识点提炼」小表 | 跳读者只看这个也能懂 |

## 4. 反例（第三章初版踩过）

| 反例 | 问题 | 改法 |
| --- | --- | --- |
| 开头直接甩 `app/` 五层目录 | 还没跑通就先看架构，挫败 | 先 30 行单文件跑通，再讲为什么要拆 |
| 11 个 Alembic 小节塞在同章 | 主线被支线淹没 | 拆成番外，正文只留一句指引 |
| 每个概念都配长段散文 | 找不到重点 | 一句话定义 + 代码 + 表格 |
| 讲 `pool_recycle` 讲了半页 | 和本章目标无关的细节 | 一行注释带过 |

## 5. 交付方式

| 场景 | 给什么 |
| --- | --- |
| 开新章 | 先给「骨架 + Step 1」，确认方向对了再展开全章 |
| 改文档 | 只给改动段落 + 前后对比，不重贴全文 |
| 代码示例 | 同步落一个 `practice/chNN/` 可运行文件，文档里链过去 |
| 长内容 | 正文只留主线，细节进 `notes/番外/` |

**默认**：完整章一次性给，但文档内部必须支持"只看前 30 行就够用"。
