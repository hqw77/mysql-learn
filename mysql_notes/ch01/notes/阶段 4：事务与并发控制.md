## 2. 核心原理：什么是事务？
假设张三给李四转账 100 元,这需要两步：

1. `UPDATE users SET balance = balance - 100 WHERE name = '张三';`
2. `UPDATE users SET balance = balance + 100 WHERE name = '李四';`

如果第一步执行完,服务器突然停电了,第二步没执行,张三的钱扣了,李四没收到,这就成了**烂账**。  
**事务的作用**：把这两条 SQL 打包成一个整体。只要有一条失败,整个包就作废（回滚）,数据库当无事发生。

### 2.1 ACID 四大特性（面试必考）
+ **A（Atomicity）原子性**：要么全成功,要么全失败。（底层靠 `undo log` 实现）
+ **C（Consistency）一致性**：转账前总金额是 1000,转账后总金额还是 1000。
+ **I（Isolation）隔离性**：张三给李四转账时,王五查余额看到的还是转账前的数据。
+ **D（Durability）持久性**：只要事务提交成功,哪怕立刻拔电源,数据也不会丢。（底层靠 `redo log` 实现）

## 3. 核心理论：并发问题与隔离级别
当多个用户同时操作数据库时,如果不加控制,会出现三种问题：

1. **脏读（Dirty Read）**：A 事务读到了 B 事务**未提交**的数据。如果 B 回滚,A 读到的就是假数据。
2. **不可重复读（Non-Repeatable Read）**：A 事务内两次读取同一行数据,结果不一样（因为 B 事务在这期间修改并提交了该行）。
3. **幻读（Phantom Read）**：A 事务内两次查询同一个范围,第二次查出了新多出来的行（因为 B 事务在这期间插入了新行）。

**MySQL 的 4 种隔离级别：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
| --- | --- | --- | --- | --- |
| **读未提交** (Read Uncommitted) | ❌ | ❌ | ❌ | 几乎不用,毫无安全性 |
| **读已提交** (Read Committed) | ✅ | ❌ | ❌ | Oracle 默认级别 |
| **可重复读** (Repeatable Read) ⭐ | ✅ | ✅ | ❌ | **MySQL 默认级别** |
| **串行化** (Serializable) | ✅ | ✅ | ✅ | 排队执行,极慢 |


_(__✅__ 表示能解决该问题,__❌__ 表示无法解决)_

## 4. 实操一：Python 代码中的事务（转账案例）
### 4.1 基本用法：`try...except...finally`
在 PyMySQL 中,默认是不自动提交事务的（即 `autocommit=False`）。执行增删改操作后,必须手动提交,否则数据不会真正落盘。



打开 `mysql_notes/ch01/code/phase4/` 文件夹（没有就新建）,创建 `transaction_test.py`。

```plain
import pymysql

conn = pymysql.connect(
    host="localhost", user="root", password="你的密码",
    database="learn_mysql", charset="utf8mb4"
)

def transfer_money(from_user, to_user, amount):
    try:
        with conn.cursor() as cur:
            # 1. 开启事务 (PyMySQL 默认不自动提交,执行 DML 语句即开启事务)
            # 也可以显式执行 cur.execute("BEGIN;")
            
            print(f"开始转账：{from_user} -> {to_user} ￥{amount}")
            
            # 步骤 1：扣钱
            cur.execute("UPDATE users SET balance = balance - %s WHERE username = %s", (amount, from_user))
            # 步骤 2：加钱
            cur.execute("UPDATE users SET balance = balance + %s WHERE username = %s", (amount, to_user))
            
            # 模拟程序崩溃（主动抛出异常）
            # 把下面这行注释掉,转账就会成功。
            raise Exception("💥 服务器突然断电,转账中断！") 
            
            # 如果上面没报错,提交事务
            conn.commit()
            print("✅ 转账成功！")
            
    except Exception as e:
        # 如果中途报错,回滚事务（撤销所有操作）
        conn.rollback()
        print(f"❌ 转账失败,已回滚。错误信息: {e}")
    finally:
        conn.close()

# 测试转账：把刚才造数据里的李四的 500 转 100 给王五
transfer_money('李四', '王五', 100)
```

**操作步骤**：

1. 先运行上面带 `raise Exception` 的代码,你会看到控制台报错回滚。
2. 去数据库里查 `SELECT username, balance FROM users WHERE username IN ('李四', '王五');`,发现余额根本没变！
3. 把 `raise Exception` 注释掉,再跑一次。查数据库,李四变成 400,王五变成 100。

### 4.2 优雅写法：`with conn:`（上下文管理器）
PyMySQL 支持上下文管理器。`with conn:` 块内的代码执行完且没有异常时,会**自动 **`commit()`；如果抛出异常,会**自动 **`rollback()`。这是生产环境推荐写法。

```plain
def transfer_money_safe(from_user, to_user, amount):
    with conn.cursor() as cur:
        # 注意：with conn: 只需包住执行的逻辑即可
        with conn: 
            cur.execute("UPDATE users SET balance = balance - %s WHERE username = %s", (amount, from_user))
            cur.execute("UPDATE users SET balance = balance + %s WHERE username = %s", (amount, to_user))
            # 如果这里发生异常,with 块会自动回滚
    print("✅ 转账成功！")
```

## 5. 实操二：模拟并发锁等待（双终端验证）
在真实的终端里感受一下“锁”。**打开两个 VS Code 终端窗口**,都登录 MySQL (`mysql -u root -p`)。或者用两个 Python 脚本同时运行。

**终端 A（锁的持有者）**：

```plain
USE learn_mysql;
BEGIN;
UPDATE users SET balance = 999 WHERE username = '张三';
-- ⚠️ 注意：这里先不要写 COMMIT;
```

**终端 B（等待者）**：

```plain
USE learn_mysql;
-- 此时去修改同一行数据
UPDATE users SET balance = 888 WHERE username = '张三';
```

**现象**：终端 B 会卡住不动,光标一直闪烁,这就是**锁等待**。因为终端 A 的事务还没提交,行锁还没释放。  
**解决办法**：在终端 A 里输入 `COMMIT;`,终端 B 会瞬间执行完毕。

**题目 2**：解释为什么银行转账绝对不能用“读未提交”的隔离级别？  
**参考答案**：  
因为“读未提交”允许一个事务读取到另一个事务尚未提交的数据。如果在转账过程中（张三扣钱已执行,李四加钱尚未执行）,银行风控系统使用了“读未提交”,看到的是张三的钱少了,而李四的钱还没增加。如果此时张三的事务回滚了,风控系统看到的数据就是错误的,会导致严重的误判甚至资金风险。

## 7. 踩坑记录与复盘
1. **坑：执行了 **`INSERT`**/**`UPDATE`**,但去数据库查不到数据。**
    - 原因：忘记执行 `conn.commit()`。
    - 解决：确保代码走到 `commit()`,或者使用 `with conn:`。
2. **坑：多终端运行同一行 **`UPDATE`**,导致代码卡死不动。**
    - 原因：另一终端持有行锁未释放（未 commit 或 rollback）。
    - 解决：去持有锁的终端提交或回滚事务。
3. **坑：死锁（Deadlock found when trying to get lock）。**
    - 原因：两个事务互相持有对方想要的锁（比如 A 锁了行 1 想更新行 2,B 锁了行 2 想更新行 1）。
    - 解决：MySQL 会自动检测并让其中一个事务回滚报错。在业务代码中,应当捕获此异常并进行重试。
